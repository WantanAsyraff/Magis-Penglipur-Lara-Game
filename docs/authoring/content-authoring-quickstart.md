# Three end-to-end content exercises

Use an isolated content branch and Godot 4.7. These are proposed exercises, not new shipped content. No experimental `.tres` or actor is added by this handbook. Use [the registration matrix](../reference/content-registration-matrix.md) to review each boundary; the steps below are sufficient to construct the content with existing schemas.

## 1. Add a spell and teach it

1. In FileSystem create a new top-level file under data/magis/spells/ using New Resource → SpellData. Call its unique spell_id `demo-study-pulse` and name Study Pulse. Do not reuse the UID of the reference spell.
2. In spell_incantation enter up, up, right, down, left, down, up. Run the library validator after baking: if another contributor has added that exact combo, choose another. Proper shared prefixes are allowed; exact duplicates are not.
3. Set delivery AREA_BURST, aoe_spell_radius 140, upfront_cost 10, cast_time .1, recovery_time .15, targeting ENEMIES and an existing academic_fields reference such as Physics. Pick an existing Texture2D icon and muted colour for discoverable UI.
4. In effects add New DamageEffect with amount 10, then New ApplyStatusEffect with status slow, duration 2, magnitude .2, REFRESH/max_stacks 1. Existing execution now supplies this entire mechanic; do not edit Player.gd. Compare thermal-kinetic.tres for the same class composition.
5. For a temporary local exercise, assign the spell to an existing subject's contained_spells, noting that this intentionally changes the shared subject content. Alternatively create a new subject/course using [the full course walkthrough](courses-and-subjects.md), expose its SpellTreeView and register the course for saves. Remove temporary subject edits before committing unless they are the intended content change.
6. Open tools/bake-spell-manifest.gd in Script editor, Ctrl+Shift+X; review its new preload. Run tools/validate-spells.gd the same way. Resolve validation errors, review prefix warnings and verify the ID appears in Spell_Library.all_spells in Remote Inspector.
7. Enter the accessible course view, buy the subject once, return to the campaign/lab context, open My Spells and equip the spell. With combat mode enabled, O opens stance and I/J/K/L provide up/left/down/right by default. Completing the valid combo executes without another confirmation in CHAINED mode. Check damage, slow and expiry on an eligible enemy/dummy and reject an invalid direction.
8. Run spell-regression, player-combo-chains and incantation-assistant scenes with --quest-test-mode. Add a test that references the new spell and checks its effect; unchanged shipped-suite counts do not prove the new content works. Export a PCK using the commands in [testing](../reference/testing-and-validation.md) and enter the same referenced test/world scene from it. Verify the spell Resource resolves in the pack and learned/equipped IDs survive a fresh-process isolated save.

## 2. Add an enemy using existing behavior

1. Create EnemyData under data/npc/enemies/definitions/, explicit enemy_id/quest_enemy_id `demo_study_sentinel`, name Study Sentinel and faction enemy.
2. Add New EnemyStatsData: positive max_health, finite movement/mitigation, and max_mana 0 for a pure melee example. Add New EnemyPerceptionData with detection_range 620, scan_interval .2 and normal target_groups. Defaults can be kept when understood; no health value should be inferred from historical guide prose.
3. Assign the existing heavy-guardian profile and guardian-melee ability. These are actual Resources at data/npc/enemies/ai-profiles/heavy-guardian.tres and data/npc/enemies/abilities/guardian-melee.tres. A unique profile/ability is needed only if modifying their shared settings.
4. Open components/NPCs/enemies/Enemy.tscn → New Inherited Scene. Save your content scene, assign the new enemy_data to its root, change sprite/frames as desired and preserve the shared component/body/ground-sensor contracts. Custom appearance can be a referenced Node2D visual_scene; it is not a replacement controller.
5. Add the definition's preload to data/npc/enemies/enemy-manifest.gd ENEMIES. No enemy baker exists. EnemyData.validate and QuestRegistry cross-reference validation should accept the identity.
6. Create SpawnData via New Resource in data/npc/enemies/spawn/: enemy_scene = your inherited scene, optional enemy_data = your definition, spawn_weight 1. On an EnemySpawner placed in a copy of the enemy arena/world, put that entry in spawn_pool, max_enemies 1, respawn false and a clear grounded marker under a Node2D parent. Wait its spawn_interval (default 3 seconds) for the first spawn.
7. F6 the copied test scene with --quest-test-mode. Ensure a player exists through the lab/world's existing spawn setup. Enter detection, cross LOS obstruction, get into root-to-root melee range, observe windup/damage/recovery, apply stun, then defeat through HitboxComponent. Check death/XP/loot once; do not manually invoke reward hooks after queue_free.
8. Run enemy-pipeline plus new definition/spawn assertions. Export a PCK and load that referenced scene. Keep the new scene/Resource/manifest if intended content; remove temporary arena changes. No EnemyCombat/AI controller copy is required.

## 3. Add an item/drop and quest using the enemy

1. Create ItemData under data/items/: unique item_id `demo_study_fragment`, name Study Fragment, item_type MATERIAL, is_stackable true, max_stack 99, optional existing icon/tag. Add to ItemManifest.ITEMS, or let the next registered enemy loot reference register it. ItemData alone has no acquisition source.
2. Create LootData under data/loot/: assign that item, drop_chance 1 for deterministic exercise, min/max_quantity 1 and no extra_drops. Assign it to the new enemy definition's loot array. This enemy is already in EnemyManifest; QuestRegistry now knows the item through its loot. Test physical pickup rather than adding a UI label.
3. New QuestData under data/quests/: unique quest_id `demo_sentinel_samples`, visible title/description, faculty TECHNOLOGY_SCIENCE, region_id bakau and hand_in_npc_id bakau_field_researcher. Add New QuestObjectiveData `defeat_demo`: type DEFEAT_ENEMY, target_id demo_study_sentinel, required_amount 2. Add `deliver_demo`: type COLLECT_ITEM, target_id demo_study_fragment, required_amount 2, collection_mode DELIVERY. Keep ordering empty to collect while killing.
4. Write offer/incomplete/complete/accepted/declined dialogue that states these exact counts. Configure a modest test reward_xp and reward_currency, no probabilistic item rewards. Do not change shipped reward values or use timeline completion to grant anything.
5. Add the QuestData to bakau-database.tres quests. Existing QuestRegistry loads that path. In the playable test room add an Area2D, attach components/quests/quest-board.gd, then assign database, region bakau and npc_id bakau_field_researcher on this QuestBoard. Its script creates its detector and collision. For a new giver instead, create/register NPCPresentation and configure a reachable QuestNPCComponent with matching faculty/identity as described in [NPCs](npcs-and-dialogue.md).
6. Play the complete sequence: View Offer → Decline (no progress/reward) → View Offer → Accept → defeat two spawned enemies → pick up both fragments → hand in. Verify delivery removes exactly two, XP/currency are awarded once and the phone records the actual decision/milestones. Repeating hand-in or overlapping the same pickup must not duplicate rewards. Test insufficient inventory space and failed save commit using isolated fixtures.
7. Run quest-pipeline, quest-accessibility and writer/reader persistence tests with --quest-test-mode. Existing catalogue-size assertions must be consciously updated only when intended registered content changes. Add specific assertions for your new quest; do not delete failing registration checks.
8. In an isolated full-game campaign profile, save after acceptance/progress and restart, then save after claim/restart and attempt replay. Use separate manual/autosave destinations and verify the exported pack too. The Bakau field lab itself is not a campaign save destination; full-game persistence testing needs a supported campaign ZoneRoot scene containing your test content. Remove fixture data and temporary world edits after verification.

All three exercises use Resources plus explicit registration/scene references. New mechanics, new database lists, course persistence allowlists and arena-to-boss integration can require small reference/code edits; those boundaries are documented rather than hidden behind “data only.”
